# Postgres is the source of record; FalkorDB is an essential, rebuildable projection

Postgres stores source versions, chunks, entities, extraction runs, reviewed claims, cached embeddings,
graph-build manifests, and the active-build pointer. FalkorDB holds a projection of approved records,
rebuilt into a **fresh graph per build** and activated only after integrity checks, so corrected or
removed facts cannot leave stale relationships behind (an in-place `MERGE` rebuild could).

The projection is replaceable but **essential at query time**: business-fact retrieval and traversal
happen only in FalkorDB. Postgres may resolve aliases and hydrate exact chunk IDs, but there is
deliberately no Postgres answer path that takes over when the graph is down; the API returns
`unavailable` instead. A silent fallback would answer from different logic than the one we verify.

## Consequences

- Each question pins one build ID; old graphs are retained until in-flight requests finish.
- Graph names are generated by the application (`<prefix>__<suffix>`), never supplied by users or LLMs.
